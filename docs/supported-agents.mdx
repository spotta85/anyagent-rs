anyagent ships a catalog of known agents. Each entry says how to find the CLI,
how to launch it in protocol mode, and the quirks that were verified against a
real install.

## Catalog

| Agent | id | CLI | Wire | Install |
|---|---|---|---|---|
| Claude Code | `claude` | `claude` | native (stream-json) | `npm install -g @anthropic-ai/claude-code` |
| Codex | `codex` | `codex` | native (app-server) | `npm install -g @openai/codex` |
| Antigravity | `antigravity` | `agy`, or its ACP server when installed | native (stream-json), ACP with the server | [antigravity.google](https://antigravity.google), then `agy install`; optional ACP server below |
| Grok | `grok` | `grok` | ACP | `npm install -g @xai-official/grok` |
| Hermes Agent | `hermes` | `hermes` | ACP | [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) |
| opencode | `opencode` | `opencode` | native (HTTP + SSE) | `brew install sst/tap/opencode` |
| Kiro CLI | `kiro` | `kiro-cli` | ACP | [kiro.dev](https://kiro.dev) |
| Qwen Code | `qwen` | `qwen` | ACP | `npm install -g @qwen-code/qwen-code` |

## Antigravity: two ways in

Antigravity has two wires, and discovery picks the richer one that is
installed:

```text
discover("antigravity")
  ├─ ACP server found  ──►  open over ACP: permissions, questions, steer,
  │                         in-process cancel, images, slash commands
  │                         (Gemini models only)
  └─ only `agy` found  ──►  open over agy's headless stream-json wire:
                            text, tools, resume, context usage, cancel by
                            respawn; every model `agy models` lists
                            → installation.upgrade names the server
```

The `agy` CLI ships with the Antigravity IDE, so most machines have it. Its
headless wire cannot prompt: in `Ask` mode every permission-gated tool is
denied by the agent itself (the tool shows as failed with its message),
`AutoApprove` launches with `--dangerously-skip-permissions`, questions are
skipped and reported as a diagnostic, and a mid-turn prompt queues. `model`
and `mode` (`accept-edits`, `plan`) are creation-time options; reopen with
the resume token to change them. Cancel kills the process and resumes the
conversation in a fresh one, about two seconds.

The ACP server is Google's own, listed in the
[ACP registry](https://github.com/agentclientprotocol/registry/blob/main/antigravity-acp/agent.json)
as `antigravity-acp`: a 314 MB download, 854 MB unpacked, searched in
`~/.local/agy-acp-server` and on `PATH`. It reuses the `agy` login: anyagent
calls its `authenticate` once per open when the server has no auth choice of
its own (about 2 seconds, no browser), or set `auth.type` in
`~/.gemini/antigravity-acp/settings.json` to skip that. With no `agy` login
either, the server opens Google's browser login and the open fails
`AuthRequired` naming `agy`, like the CLI does. When `agy` is found
but the server is not, the installation carries
`upgrade: Some(MissingAgent)` with the download hint, so an app can offer the
richer path without hard-coding anything:

```rust
let agent = report.require("antigravity")?;
if let Some(upgrade) = &agent.upgrade {
    ui.offer_install(&upgrade.name, &upgrade.install_hint);
}
```

To force the headless CLI while the server is installed, point the catalog at
it: `ANYAGENT_ANTIGRAVITY_BIN=~/.local/bin/agy`.

Google's Antigravity terms restrict third-party tools driving a personal
Antigravity login; the ACP server is Google's sanctioned client path. Apps
should surface that choice to their users.

<Note>
`pi` is provider-key based: log in with `/login <provider>` inside the CLI,
or set the provider's API-key variable.
</Note>

<Note>
Compaction (`session.compact()`) is native-adapter only: claude, codex,
opencode, and pi each have their own way to summarize a session, and the four
are verified live except pi's success path. ACP has no compaction in schema
1.7, so ACP agents refuse with `UnsupportedFeature` — kiro's own `/compact`
command runs asynchronously with nothing to wait on.
</Note>

<Note>
Kiro exposes `effort` (low / medium / high / xhigh / max) as a live config
option on models that have it, even though it advertises none over ACP: the
adapter reads the current level from
kiro's metadata frames and switches it by running `/effort <level>` as a
prompt between turns. A switch made mid-turn waits for that turn to end, and
a prompt sent while the switch runs waits behind it.
</Note>

<Note>
Codex opts into the app-server's experimental API, which is what unlocks its
questions (`requestUserInput`). Approval policy and sandbox switch live (they
ride every `turn/start`), images ride as `localImage` items, client MCP servers
ride `-c mcp_servers.…` launch overrides (stdio and HTTP; no SSE), and
`rollback` maps to `thread/revert` (a cut before a kept turn). Files are
never restored.
</Note>

<Note>
Hermes gates only its file tools behind permission requests — its terminal
tool runs without asking, so a denied write does not stop the agent from
writing via shell. Sandbox accordingly if that matters to your app.
</Note>

<Note>
opencode runs native: anyagent starts `opencode serve` on a private localhost
port per session, gated by a per-session secret, and drives its HTTP + SSE
wire. This adds permissions, questions, rollback, fork, slash commands, plans,
and context usage over the ACP path, and task-tool child sessions nest under
their spawning tool as subagents. It does not steer (the engine queues
mid-turn prompts instead), and it has no plan quota. Pass a model with
`configure("model", "provider/id")`; opencode's own free `opencode/…` models
need no extra key. To drive it over ACP instead, build it with
`AgentInstallation::acp("opencode", path, ["acp"])`.
</Note>

## Any other ACP agent

You don't need a catalog entry to use an agent that speaks
[ACP](https://agentclientprotocol.com). Build the installation yourself:

```rust
use anyagent::{AgentInstallation, Runtime, SessionOptions};

let agent = AgentInstallation::acp(
    "my-agent",                    // display name
    "/usr/local/bin/my-agent",     // executable
    vec!["acp".into()],            // args that put it in ACP mode
);

let (session, events) = Runtime::new()
    .open(&agent, SessionOptions::in_dir("."))
    .await?;
```

Everything downstream — events, requests, capabilities — is identical. What you
lose is the catalog's verified quirks: launch flags, login markers, and auth
error hints. Guessed flags don't ship, so an unverified agent gets the plain
launch path.

## Pointing at a specific binary

Every catalog entry reads an environment variable first, which is the easiest
way to test a build that isn't on `PATH`:

```bash
ANYAGENT_CLAUDE_BIN=/path/to/claude cargo run --example probe
```

The pattern is `ANYAGENT_<AGENT>_BIN`. Or skip discovery entirely with
`AgentInstallation::at(id, executable)`.

## Several logins of the same agent

Give each one its own config directory:

```rust
SessionOptions::in_dir(".").config_home("/path/to/work-account")
```

anyagent sets the agent's own config-home variable (`CLAUDE_CONFIG_DIR`,
`CODEX_HOME`, …) for that process. Opening an agent whose profile has no such
variable with `config_home` set fails with `InvalidConfiguration` — an
isolation request is never silently dropped.
